# SFLIX-20261120-023 – Analyse: Performance der STEFFLIX-Tools (Desktop, C#)
- Erstellt am: 2026-11-20
- Absender: Planung
- Empfänger: Architekt
- Priorität: MEDIUM
- Status: COMPLETED
- Aufgabenbeschreibung: Der Benutzer empfindet die Tools in STEFFLIX.exe als sehr langsam und ineffizient. Die C#-Anwendung (SFLIX_Tools/SflixTools/src, C# 5 / .NET Framework 4.x) auf Performance prüfen, ohne Code zu ändern. (1) Seriell ausgeführte Abläufe, die sich asynchron oder parallel ausführen liessen (Dateisystem-Scans, Hashing/Vergleiche, Netzwerk, ffmpeg/ffprobe-Aufrufe, Plakat/Cover-Downloads); ineffizienter Code (wiederholtes Lesen derselben Dateien, O(n²)-Schleifen, String-Verkettung in Schleifen, unnötige Kopien, fehlender Cache, synchrones I/O im UI-Thread, Invoke-Fluten, Log/ListView-Updates je Eintrag); Stellen, wo Multithreading sinnvoll wäre und wo nicht (UI-Thread-Bindung WinForms, NAS/SMB verträgt nur begrenzte Parallelität, ffmpeg CPU-lastig, Abbruch und Fortschritt). (2) Laden der Tools: Werden alle Tool-Seiten/Controls/Daten beim Start erzeugt und im Hintergrund bereitgehalten, oder erst beim Öffnen (lazy)? Startzeit von STEFFLIX.exe und Speicherbedarf mit einbeziehen (MainForm.cs, Desktop.cs, Controls.cs, WebView2-Initialisierung). Wo möglich messen (perf-messer, nur mit Testumgebung .claude/testenv und SFLIX_DIR; laufende STEFFLIX.exe des Benutzers nicht stören), sonst begründet aus dem Code schätzen.
- Technischer Kontext: Benutzerauftrag 20.11.2026. Nur Analyse; Umsetzung erst nach Benutzerentscheid über die Planung. Der Benutzer kann konkrete langsame Tools nachliefern (siehe Planung).
  Ergänzung Benutzer 20.11.2026: Keine bestimmten Tools benennbar; Symptome: einige Tools laden langsam, andere blockieren die Oberfläche, bis der Code abgearbeitet ist. Alle Tools allgemein prüfen, besonders auf Arbeit im UI-Thread.
- Betroffene Dateien: SFLIX_Tools/SflixTools/src/MainForm.cs, SFLIX_Tools/SflixTools/src/Desktop.cs, SFLIX_Tools/SflixTools/src/Controls.cs, SFLIX_Tools/SflixTools/src/Core.cs, SFLIX_Tools/SflixTools/src/Util.cs, SFLIX_Tools/SflixTools/src/EpisodeTask.cs, SFLIX_Tools/SflixTools/src/DownloadTask.cs, SFLIX_Tools/SflixTools/src/MediaCheckTask.cs, SFLIX_Tools/SflixTools/src/DuplicateTask.cs, SFLIX_Tools/SflixTools/src/DataTask.cs, SFLIX_Tools/SflixTools/src/ConvertTask.cs, SFLIX_Tools/SflixTools/src/AlbumCoverTask.cs, SFLIX_Tools/SflixTools/src/Ffmpeg.cs, SFLIX_Tools/SflixTools/src/MediaCache.cs, SFLIX_Tools/SflixTools/src/LogView.cs
- Erwartetes Ergebnis: Bericht als Entscheidungsvorlage für den Benutzer über die Planung: Befunde je Datei/Tool mit Ursache, geschätztem Gewinn, Aufwand und Risiko, priorisiert (schnelle Gewinne zuerst); klare Antwort auf Frage 2 (was wird beim Start geladen, was lazy) mit Empfehlung; Vorschlag, in welchen Paketen die Entwicklung umsetzt (Aufträge nach gemeinsamen Dateien gebündelt); Messwerte oder Kennzeichnung als Schätzung; Grenzen (C# 5, .NET 4.x, NAS, Bitdefender bei Testläufen).
- Durchgeführte Arbeiten: Analyse ohne Codeänderung. Grundaufbau gut: Aufgaben im eigenen Thread, Dialoge per Invoke, Protokoll gebündelt (100 ms, RTF), Workers parallel, Schnelltest bei Duplikaten, MediaCache. Player und Tools teilen einen UI-Thread (DesktopHost): Blockaden in den Tools frieren auch den Player ein. Befunde: (P1, hoch) DataTask.Crawl: File.Exists/Directory.Exists und Attribute je Eintrag (je eine SMB-Abfrage), ShrinkPreview liest jedes Vorschaubild bei jedem Einlesen ganz (ReadAllBytes+Decode); (P2, UI-Thread) Tools-Aufbau liest version.js, Undo-Protokoll, Kategorien mit Attributen, Cachegrösse, license.js/install.js, downloads.json synchron; DownloadAddDialog durchsucht 3 Ordnerebenen synchron (StefflixFolders); EpisodePlanDialog 2 Abfragen je Datei; CleanupDialog.UpdateTotal FileInfo je Datei bei jedem Häkchen; AlbumCoverDialog lädt Bilder (ggf. ffmpeg) synchron; (P3) Scans ohne Metadaten: CollectFiles/MediaFacts.Basic/CleanupTask/MergeTask FileInfo je Datei, MediaCache liest version.json je Datei; (P4) grosse Ergebnislisten ohne VirtualMode; (P5) klein: Tools-Fenster wird bei jedem Öffnen neu gebaut, Albumcover-Extraktion seriell, CompareView prüft seriell, Font-Leck in LogPanel.AppendEntry. Frage 2: Tools werden erst beim ersten Öffnen gebaut (alle Reiter auf einmal), beim Schliessen verworfen.
- Tests und Ergebnisse: Messung Release-EXE 4.0.6 mit Testumgebung (lokal, je 3 Läufe): Tools-Fenster 0,19-0,31 s, EXE 62 MB; Player-Fenster 0,16-0,19 s, EXE 58 MB plus 6 WebView2-Prozesse 366-395 MB. NAS nicht gemessen (kein Testordner genannt): Gewinne P1-P3 sind Schätzungen.
- Verbleibende Risiken: P1 muss data.js byte-gleich halten (Vergleich vorher/nachher an der Testumgebung); P4 nur bei sehr grossen Listen lohnend.
