# SFLIX-20261120-024 – Analyse: eigener Titel im Bild-im-Bild des Desktops (eigenes BiB-Fenster, Document Picture-in-Picture)
- Erstellt am: 2026-11-20
- Absender: Prüfung
- Empfänger: Architekt
- Priorität: LOW
- Status: COMPLETED
- Aufgabenbeschreibung: Der Benutzer möchte im BiB des Desktops statt "Datei auf Ihrem Gerät" den Videotitel sehen. Das native BiB von Chromium zeigt in der Titelzeile die Herkunft der Seite (bei file:// "Datei auf Ihrem Gerät"); weder Seite noch Media-Session-Metadaten können das übersteuern (DEC-344). Auftrag des Benutzers: zwei Varianten analysieren, nichts umsetzen.
  1. Eigenes BiB-Fenster im Desktop (STEFFLIX.exe): randloses TopMost-Fenster mit eigener Titelzeile und Bedienelementen (heute im nativen BiB: -10 s, Pause, +10 s, Fortschrittsleiste, Zeit, Stumm, Vor/Zurück über Media Session, Minimieren, Zurück zum Tab, X). Fragen: Wie kommt das Video hinein (zweite WebView2, Übergabe von Zeit/Zustand, gleiche Datei neu laden), Synchronisation mit player.js (Vor/Zurück, Weiterschauen, Fortschritt), Verhalten von Minimieren/Wiederherstellen (heute PlayerForm.OnPip), Ressourcen, Aufwand, Risiken; Browser und App behalten das native BiB.
  2. Document Picture-in-Picture (documentPictureInPicture.requestWindow): Unterstützt WebView2 (Version im Projekt 1.0.4258.31 bzw. Laufzeit) das? Zeigt die Titelzeile auch dort nur die Herkunft? Liesse sich die Variante unter file:// nutzen?
  Verworfen vom Benutzer: virtueller Hostname statt file:// (Herkunft und damit gespeicherte Daten würden wechseln).
- Technischer Kontext: Prüfung SFLIX-20261120-016/-022: natives BiB funktioniert (Minimieren, Symbol app_pip.ico, Wiederherstellen, Vor/Zurück, X; Benutzer hat Bedienelemente per Screenshot bestätigt). Offener Fehler SFLIX-20261120-020 (BiB bleibt nach Medien- oder Seitenwechsel verwaist offen) betrifft dieselbe Stelle in player.js. Testverfahren für BiB in docs/TESTING.md (CDP mit userGesture, Win32, Windows-Mediensteuerung).
- Betroffene Dateien: SFLIX_Tools/SflixTools/src/PlayerForm.cs, sflix_sys/js/player.js
- Abhängigkeiten: SFLIX-20261120-016
- Erwartetes Ergebnis: Analyse mit Empfehlung je Variante (Machbarkeit, Aufwand, Risiken, Auswirkungen auf Browser/App); Vorschlag als Entscheid zur Freigabe durch den Benutzer
- Durchgeführte Arbeiten: Bewertet: (1) eigenes Fenster mit zweiter WebView2: gross, Nachladen der Datei mit Positionsübergabe, Ton kurz doppelt, zweiter Seitenprozess, Synchronisation von Vor/Zurück und Fortschritt über die Brücke - nicht empfohlen; Variante Player-Fenster wird klein (A3) gibt den Titel ebenfalls, vom Benutzer früher nicht gewählt. (2) Document PiP: am Fenster geprüft, API vorhanden, requestWindow scheitert ohne vom Programm bereitgestelltes Fenster; mit NewWindowRequested/NewWindow in einem eigenen TopMost-Fenster wäre der Titel (Form.Text), das Symbol, Minimieren und eine stufenlose Lautstärke in eigener Hand und das Video zieht ohne Nachladen um - ungeprüft, Prototyp nötig. Browser: Chrome könnte Document PiP direkt nutzen, App behält natives BiB.
- Tests und Ergebnisse: CDP-Test mit Testumgebung, Release-EXE 4.0.6, Runtime 157: typeof documentPictureInPicture = object; requestWindow: InvalidStateError 'no window'; der Player navigierte dabei auf about:blank (OnNewWindowRequested).
- Verbleibende Risiken: Document PiP über ein Fenster des Programms ist in WebView2 nicht dokumentiert; Nebenbefund: jede neue Fensteranfrage mit about:blank ersetzt heute die Seite des Players.
- Folgeschritt: Benutzer entscheidet über einen Machbarkeitsprototyp für Document PiP mit eigenem Fenster.
